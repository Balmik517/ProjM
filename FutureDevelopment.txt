Yes. At this point, I would **stop adding everything in one large change**.

Because `ProjM` is also being used to test your **Decomposition Advisor**, the Git history itself should become part of the benchmark. Your advisor already uses **git co-change** as a clustering signal, with co-change weighted strongly during community detection. 

So the next evolution should look like a **real application that grew over time**.

## My recommendation

Keep every existing package unchanged:

```text
com.pma.spring.web.*
```

Then introduce new domain-oriented packages gradually:

```text
com.pma.spring.billing
com.pma.spring.notification
com.pma.spring.reporting
com.pma.spring.integration
com.pma.spring.audit
com.pma.spring.task
```

Don't add all six at once.

Build them in **feature waves**.

# Phase 8 — Introduce the legacy problems gradually

This is where I would intentionally evolve the application rather than dropping all smells into one commit.

### Commit 1

Introduce a shared utility:

```text
refactor: introduce common legacy utility
```

### Commit 2

Introduce cross-domain service dependency:

```text
feat: connect billing with project lifecycle
```

### Commit 3

Introduce broad transaction:

```text
feat: make project completion workflow transactional
```

### Commit 4

Add audit + notification inside that transaction:

```text
feat: extend project completion workflow
```

### Commit 5

Add reporting to the same workflow:

```text
feat: generate completion report from project workflow
```

Now you have historical evidence showing how the architecture became coupled.

That's much better than creating:

```text
GodService.java
```

in a single giant commit.

# One important rule

**Do not create 50 meaningless commits just to generate Git history.**

Every commit should represent a believable engineering change:

```text
feature
bug fix
integration
refactor
performance improvement
transaction change
scheduled job
reporting enhancement
```

And keep each change focused.

For example, this is good:

```text
feat: add payment processing
```

This is bad:

```text
feat: add billing payment notification reporting audit integration
```

The latter destroys your co-change signal because everything changes together.


That gives you **three dimensions of legacy**:

```text
Structural legacy
       +
Runtime/data coupling
       +
Historical coupling
```

And that is much more valuable for your Decomposition Advisor than simply making the project bigger.

One thing I would do before starting Phase 1 is create a **feature roadmap of around 15–20 commits**, so every future commit has a deliberate architectural purpose and the resulting Git history becomes a controlled benchmark rather than random project growth.
